# onepack catalog

Generated by scripts/build.py from guides/ and the built plugins. Do not edit by hand.

## How to choose

Decide two things separately, then combine:

1. **Spec layer (group `sdd`)** — does the work need a written agreement before code?
   - No: small fix, script, spike, one-file change → no SDD.
   - Yes, existing codebase, change by change → **openspec**.
   - Yes, greenfield or large feature, full plan with gates → **speckit**.
2. **Method (group `method`)** — how should the agent work?
   - Human in the loop, spec/tickets in a tracker, tdd, review → **pocock**.
   - Hard engineering (perf, forensics, subtle bugs, behaviour-preserving refactors), long or parallel runs, Claude usage not a concern → **pstack**.
   - Simple work → no method pack.
3. **Tool packs (no group)** — combine with anything when the task needs them:
   - Studying how an existing app works, to spec your own version → **rea**.

**Default to fewer packs.** "No pack" is a valid answer: plain Claude Code plus the always-available own skills covers most small work. Each method pack adds tokens to every session in the repo (pocock ~1.5k, pstack ~4.4k).

**Rules:** at most one pack per group per repo. Avoid two spec systems: with an SDD framework, do not also use Pocock's `to-spec` / `to-tickets`.

## Always available (own skills, no pack needed)

- `/mirror` — restate a long or fuzzy brief before starting (problem, goals, limits, gaps).
- `/inspo` — prior art: similar GitHub repos and X posts before building.
- `/knowledge-sources` — research scoped to trusted legal/tax sources, with verified citations.
- `/file-updater` — roll a DOCX/XLSX/PPTX report to the next period.
- `/brand-dna` — extract a brand from a URL and apply it to a deliverable.

## Packs

### pocock — group `method`, plugin

**What:** Matt Pocock's skills for disciplined engineering with a human in the loop: align first, then spec, tickets, build test-first, review. "Skills for real engineers", not vibe coding.

**Choose when:**
- A feature or change in a real codebase where you want to stay in control of each step.
- You want a spec and tickets in an issue tracker (GitHub, GitLab or local files).
- Bug hunting with a gated loop (`diagnosing-bugs`), test-first work (`tdd`), architecture review.
- A big, foggy effort that spans sessions (`wayfinder`).

**Avoid when:** you only need a quick script or a one-file change (plain Claude is enough); you want agents to run long and parallel on their own (pstack fits better).

**Workflow:**
1. Once per repo: `/pocock:setup-matt-pocock-skills` (issue tracker, labels, docs folder).
2. Align: `/pocock:grill-with-docs` (code; updates glossary and ADRs) or `/pocock:grill-me` (non-code).
3. `/pocock:to-spec` → spec in the tracker. 4. `/pocock:to-tickets` → tracer-bullet tickets.
5. `/pocock:implement` (one ticket set: drives `tdd`, ends with `code-review`) or `/pocock:implement-spec` (whole spec, parallel subagents).
- Bugs: `/pocock:diagnosing-bugs`. Big effort: `/pocock:wayfinder`. After a session: `/pocock:retro`.

**Cost:** ~1.5k tokens added to every session in the repo. Mostly user-invoked skills, so little else until used.

**Combines with:** either SDD framework; with Spec Kit or OpenSpec, use their spec flow and keep Pocock for `grill-*`, `tdd`, `code-review`, `diagnosing-bugs` (skip `to-spec` / `to-tickets` to avoid two spec systems).

**Skills (27, invoke as `/pocock:<name>`):**

- `ask-matt` — Ask which skill or flow fits your situation
- `diagnosing-bugs` — Diagnosis loop for hard bugs and performance regressions
- `grill-with-docs` — A relentless interview to sharpen a plan or design, which also creates docs (ADR's and glossary) as we go
- `triage` — Move issues and external PRs through a state machine of triage roles, categorise, verify, grill if needed, and write agent-ready briefs
- `improve-codebase-architecture` — Scan a codebase for deepening opportunities, present them as a visual HTML report, then grill through whichever one you pick
- `setup-matt-pocock-skills` — Configure this repo for the engineering skills: set up its issue tracker, triage label vocabulary, and domain doc layout
- `tdd` — Test-driven development. Use when the user wants to build features or fix bugs test-first, mentions "red-green-refactor", or wants integration tests
- `to-spec` — Turn the current conversation into a spec and publish it to the project issue tracker: no interview, just synthesis of what you've already discussed
- `to-tickets` — Break a plan, spec, or the current conversation into a set of tracer-bullet tickets, each declaring its blocking edges, published to the configured tracker (edges as text in one file per ticket locally, or native blocking links on a real tracker)
- `wayfinder` — Plan a huge chunk of work (more than one agent session can hold) as a shared map of decision tickets on your issue tracker, and resolve them one at a time until the way to the destination is clear
- `implement` — Implement a piece of work based on a spec or set of tickets
- `implement-spec` — Implement the result of /to-spec and /to-tickets in code
- `prototype` — Build a throwaway prototype to answer a design question
- `research` — Investigate a question against high-trust primary sources and capture the findings as a Markdown file in the repo
- `domain-modeling` — Build and sharpen a project's domain model
- `codebase-design` — Shared vocabulary for designing deep modules
- `code-review` — Review the changes since a fixed point (commit, branch, tag, or merge-base) along two axes: Standards (does the code follow this repo's documented coding standards?) and Spec (does the code match what the originating issue/spec asked for?)
- `pr` — Use when writing a PR body
- `retro` — Conduct a retrospective on a coding session
- `wizard` — Generate an interactive bash wizard that walks a human through steps only they can perform
- `grill-me` — A relentless interview to sharpen a plan or design
- `grilling` — Grill the user relentlessly about a plan, decision, or idea
- `handoff` — Compact the current conversation into a handoff document for another agent to pick up
- `teach` — Teach the user a new skill or concept, within this workspace
- `to-questionnaire` — Turn a decision you can't fully answer into a questionnaire for someone else to fill in
- `wait-what` — Stop. That last message did not land: re-pitch it
- `writing-for-agents` — Writing documents for agents

### pstack — group `method`, plugin

**What:** Lauren Tan's (poteto) pstack: "if you want to go fast, go deep first". One entry skill, `poteto-mode`, picks one of 23 playbooks (bug fix, perf, feature, refactoring, runtime/trace forensics, hillclimb, babysit a PR stack, eval, visual parity…) and pulls in ~30 engineering principles and verification skills as needed.

**Choose when:**
- Hard engineering: subtle bugs, performance, memory leaks, profiling traces, refactors that must preserve behaviour.
- You want runtime evidence and verification before "done", and fewer lines of code.
- You will run agents for long stretches or in parallel (`swarm`, `arena`, overnight "land the stack").

**Avoid when:** you want a spec/ticket trail (use Pocock or an SDD framework); the work is small; you need to keep Claude usage low.

**Workflow:**
1. `/pstack:poteto-mode <task, with the evidence you expect>`: it chooses the playbook and runs the other skills itself.
2. Unsure which skill fits: `/pstack:poteto-help`.
- `/pstack:setup-pstack` has nothing to configure in Claude Code (model routing is a Cursor rule); skip it.

**Claude Code caveats:** built for Cursor. Its multi-model routing (Grok for code delegates) falls back to the session model, and it spawns many subagents, so expect **higher Claude usage** than Pocock. Cursor-only steps (Bugbot, cloud agents, automations) are skipped.

**Cost:** ~4.4k tokens added to every session in the repo (many model-invoked principle skills), plus subagent runs.

**Combines with:** OpenSpec or Spec Kit for the spec layer; pstack then executes and verifies each task.

**Skills (58, invoke as `/pstack:<name>`):**

- `architect` — Sketch types, signatures, and module structure before code, then stay in the loop while implementation fills in
- `arena` — Spawn N parallel candidates at the same task, pick a base, graft the strongest parts of the losers into it
- `automate-me` — Use for \"automate me\", \"create/update/refresh my -mode skill\", \"turn/capture my preferences or working style into a skill\", or wanting agents to follow how the user works
- `benchmark-checklist` — Vet a perf measurement (limiter, tuning, limits, errors, repeatability, relevance, and whether the work happened) before you report or act on it
- `blast-radius` — Find what a change could break somewhere else before it ships, beyond the diff, and prove the one fact it's safe because of by running real code instead of writing it up
- `bro` — Restate the last message in plain human language, with no jargon
- `correct` — Find the mistakes agents keep repeating in this repo and make each one impossible
- `create-formal-verification-skill` — Generate a project-local skill that formally verifies the code where a bug costs the most and tests reach the least, in any language, with whichever verification tool fits
- `create-verification-skill` — Generate a project-local verification skill that drives your app the way a user does — any language, framework, or platform
- `figure-it-out` — Design an auditable playbook when no narrower one fits: a large migration, an ambitious multi-part change, or work a human reviews after stepping away
- `how` — Use for \"how does X work\", code walkthroughs before changing something, and placement / ownership / layering questions (\"where should this live\", \"which package owns this\", \"is this the right layer\")
- `in-your-own-words` — Restate in your own words what you think the user's goals are and what problem they're trying to solve
- `interrogate` — Use for \"interrogate\", \"adversarial review\", \"multi-model review\", \"challenge this\", \"stress test this code\", \"find blind spots\", or \"tear this apart\"

- `maintain-formal-verification-skill` — Bring a project's formal verification back in line with the code after the code changes: find the commits that touched verified code, update the model, harness, or properties to describe the code as it is now, rerun, and say whether each failure is drift in the verification or a bug in the code

- `make-bot-ui` —  Use when building a custom UI (page, dashboard, buttons) that should wake a Grok Bot over a webhook, when the user must provide a webhook sender key, or when exposing that UI on Tailscale

### speckit — group `sdd`, cli

**What:** GitHub Spec Kit. Full spec-driven pipeline with phase gates: constitution → specify → clarify → plan → tasks → analyze → implement → converge. Files live in the repo (`.specify/`, `specs/<feature>/`). OpenSpec describes it as "thorough but heavyweight".

**Choose when:**
- Greenfield product or a large new feature where you want the full trail: principles, spec, technical plan, task list, consistency check.
- Several people or agents must work from the same written plan.
- You want hard gates before code (clarify, analyze, checklists).

**Avoid when:** small or iterative changes to an existing codebase (OpenSpec is lighter); exploratory prototypes.

**Workflow:**
1. Once: `/speckit-constitution <project principles>`.
2. Per feature: `/speckit-specify <what and why, not how>` → `/speckit-clarify` (if gaps) → `/speckit-plan <tech choices>` → `/speckit-tasks` → `/speckit-analyze` (optional) → `/speckit-implement` → `/speckit-converge` until converged.
- Extras on demand: `/speckit-checklist`, `/speckit-taskstoissues`; extensions `bug` and `assess` (`specify extension add …`).

**Cost:** 0 outside the repo; skills load only when typed.

**Combines with:** Pocock (`grill-*` before `specify`, `tdd` / `code-review` during implement) or pstack (`poteto-mode` to execute and verify tasks).

### openspec — group `sdd`, cli

**What:** OpenSpec (Fission-AI). Lightweight spec layer: "fluid not rigid", "iterative not waterfall", "built for brownfield not just greenfield". Each change is a folder (`openspec/changes/<name>/`: proposal, spec deltas as ADDED/MODIFIED requirements with SHALL + WHEN/THEN scenarios, design, tasks) that is archived into the living specs when done.

**Choose when:**
- Changes to an existing codebase, one at a time, with a short written agreement before code.
- You want specs that stay current with the code (archive merges each change into `openspec/specs/`).
- You want less ceremony than Spec Kit.

**Avoid when:** you need a full upfront plan for a large greenfield product with formal gates (Spec Kit); a trivial fix.

**Workflow:**
1. `/opsx:explore` (optional): think the change through.
2. `/opsx:propose <change-name>` → proposal, spec deltas, design, tasks.
3. `/opsx:apply` → works through the task list.
4. `/opsx:archive` → merges the deltas into the specs and archives the change.
- More commands (`new`, `continue`, `ff`, `verify`, `onboard`): `openspec config profile`, then `openspec update`.

**Cost:** 0 outside the repo; commands load only when typed.

**Combines with:** Pocock (`grill-*` before `propose`, `tdd` / `code-review` during apply) or pstack (`poteto-mode` during apply).

### rea — no group (combines with anything), mcp

**What:** REA ("Reverse Engineer Anything", morluto/rea): one MCP server to study how an application works, from its runtime behaviour and JavaScript down to native binaries (optionally through Hopper, Ghidra or IDA).

**Choose when:** you need to understand how an existing app or feature behaves to write a spec for your own implementation (e.g. studying an app's flows and network API before rebuilding the idea).

**Avoid when:** the task does not involve understanding an existing application.

**Workflow:** `onepack add rea` registers the server for this folder only (Claude Code local scope, never committed) and installs Electron globally if missing, to run Electron apps (an original and your rebuild) side by side; REA itself does not need it. Then ask the agent to analyse the target with REA and turn the findings into a spec (e.g. `/speckit-specify`).

**Cost:** an MCP server's tool descriptions load in sessions in that folder; it runs through `npx rea-agents@latest`, so it is always the latest release (Node.js needed). Electron takes ~270 MB once, shared by every folder; `onepack update` keeps it current.

**Combines with:** anything (no group); typical pair: speckit or openspec for the spec.
